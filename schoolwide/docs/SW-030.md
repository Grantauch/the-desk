# SW-030 — Staff authentication and RBAC boundary

Status: implementation batch. This layer proves staff identity, server-side sessions, role capabilities, and resource scope before any Schoolwide Hall Pass or Check-In endpoint exists.

## Boundary

SW-030 starts from verified SW-020 head `ff0a3cf5223d14ab01237507eb88e4d91789356d` and remains inside the isolated `schoolwide/` application lane.

Legacy Apps Script Hall Pass, the production workbook, the stable `/exec` deployment, grant-desk.com student routing, real student data, PIN material, and Classroom synchronization are outside this batch.

## Identity contract

Authentication and authorization are separate decisions.

1. An identity provider verifies an external staff assertion.
2. GrantDesk maps the provider's immutable subject to `users.google_subject_id`.
3. Email and display name are metadata only; they never select authorization identity.
4. The user, organization, and staff profile must all still be active when a session is created or used.
5. A successful identity match alone grants no school access.

`StaffIdentityProvider` is provider-isolated. CI uses a synthetic verifier. The default runtime provider is deliberately disabled and fails closed. SW-030 does not create a Google OAuth/OIDC client, store Google tokens, or claim production Google sign-in evidence.

A real Google identity adapter can later satisfy the same interface without changing Schoolwide role or resource-scope rules.

## Session contract

`006_staff_sessions.sql` adds opaque server-side staff sessions.

- The client receives a cryptographically random 32-byte opaque token.
- PostgreSQL stores only its SHA-256 hash, never the plaintext token.
- Sessions have bounded expiry; the implementation default is eight hours and configuration is constrained to one minute through 24 hours.
- Revoked, expired, disabled-user, inactive-staff, and inactive-organization sessions fail closed.
- Session rotation atomically revokes the old session and creates a replacement linked by `rotated_from_session_id`.
- Sign-out revokes the server-side session.
- Each session carries a correlation ID for later audit integration.
- `last_used_at` is operational session metadata, not an authorization cache.

Roles are intentionally **not** copied into `staff_sessions`. Current role grants are re-read from PostgreSQL on every authenticated request so revocation or expiry takes effect without waiting for the session to expire.

## Authorization contract

Authorization = current capability **and** current resource scope.

### Teacher

Teacher capability requires:

- a current `TEACHER` school role grant for the section's school; and
- a current, non-revoked `section_staff_assignments` row for that exact section.

Changing a URL, query parameter, request body, or client header cannot widen the section scope.

Primary teacher, co-teacher, support, and substitute assignment shapes remain database data. Ordinary teacher capabilities still require a TEACHER school role. Temporary substitute coverage can therefore be represented with effective-dated role + section assignment records without sharing another teacher's login. No substitute UI is implemented here.

### Security

Baseline SECURITY capability is school-scoped and minimal:

- `security.live.read`
- `security.student.lookup_live`
- `security.destination.read`

SW-030 deliberately does not grant teacher capabilities, admin configuration, force-close, mark-located, or request-return behavior. Those operational actions require later product/service decisions.

### Administrator

ADMIN capability applies only to schools with an explicit current ADMIN role grant. Organization membership alone does not create implicit school access, and an admin for School A does not automatically become an admin for School B.

### System

`SYSTEM` exists as a role vocabulary item but has no interactive user capabilities in SW-030. Later service-principal/background-work design must remain narrowly scoped.

## Proof routes

These are bounded read/auth proof surfaces, not finished product APIs:

- `POST /auth/session`
- `POST /auth/session/rotate`
- `DELETE /auth/session`
- `GET /api/me`
- `GET /api/sections/:sectionId/teacher-context`
- `GET /api/schools/:schoolId/security-context`
- `GET /api/schools/:schoolId/admin-context`

They exist to prove backend authorization against forged HTTP requests before Hall Pass/Check-In mutations are introduced.

## Security properties exercised by integration tests

The PostgreSQL + Fastify integration suite proves:

- unauthenticated resource access is rejected;
- immutable provider subject, not asserted email, selects the canonical staff identity;
- plaintext session tokens are not stored;
- disabling a user invalidates an existing session;
- revoked and expired role grants stop authorizing immediately;
- a teacher cannot access an unassigned section in the same school;
- a teacher cannot cross into another school in the same organization or another organization;
- organization membership without a school role grants no school access;
- SECURITY can reach the security proof surface but not teacher/admin proof surfaces;
- ADMIN is limited to explicitly granted schools;
- a current co-teacher assignment works while expired/revoked assignment fails;
- forged client role/capability/school/section claims do not widen access;
- rotation invalidates the old session;
- sign-out invalidates the replacement session;
- expired sessions fail closed.

SW-020 relational/tenant tests continue to run alongside these tests.

## Evidence level

Current SW-030 evidence is synthetic integration/CI evidence only. It is not production Google sign-in, school staff field use, pilot evidence, or Schoolwide production evidence.
